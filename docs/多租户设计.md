# 多租户设计

## 1. 隔离模型的选择

| 模型 | 做法 | 成本 | 适用 |
|---|---|---|---|
| Silo | 每租户一个数据库 | 运维成本最高 | 强合规、大客户 |
| Bridge | 每租户一个 schema | 迁移和连接管理复杂 | 中等规模 SaaS |
| **Pooled** | 共享表 + `tenant_id` | 成本最低，依赖强制隔离 | 本项目的规模 |

本项目选择 **Pooled**：单库、单 schema、所有业务表带 `tenant_id`。
在 0–100 人公司的 SaaS 场景里，Silo/Bridge 的运维成本换不来收益。

## 2. 隔离的三层强制

### 2.1 入口：租户来自凭证，不来自请求体

JWT 里带 `tid`（租户）、`sub`（用户）、`role`。`TenantFilter` 解析后写入
`TenantContext`，请求体里的任何 `tenantId` 都不会被信任。

### 2.2 连接：每次取连接都设置 session 变量

`TenantAwareDataSource` 包装 Hikari：

```text
getConnection()
  → RESET app.tenant_id; RESET app.platform_admin
  → set_config('app.tenant_id', '<uuid>', false)   或   set_config('app.platform_admin','true',false)
  → 返回代理连接
close()
  → RESET 两个变量，再归还连接池
```

这样即使连接被池复用，也不会把上一个租户的身份带过去。

### 2.3 数据库：RLS 兜底

所有业务表启用行级安全：

```sql
USING (
    current_setting('app.platform_admin', true) = 'true'
    OR tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
)
```

关键点：应用连接使用 **非超级用户** `helpdesk_app`。PostgreSQL 的超级用户会绕过 RLS，
如果用 `postgres` 跑应用，这套策略就是摆设。

## 3. 平台管理员

平台管理员属于 `platform` 租户，JWT 的 role 是 `PLATFORM_ADMIN`。
连接上设置 `app.platform_admin=true`，RLS 放行跨租户读取。

这条路径只用于运营视角（租户列表、用量），业务接口仍然要求 `tenant_id`。

## 4. 配额与公平性

- **限流**：Redis + Lua 固定窗口，key 为 `helpdesk:rl:<tenantId>:<minute>`；
- **预算**：`usage_event` 按月汇总，超过 `tenant.monthly_token_budget` 返回 429；
- **异步任务**：索引任务按租户入 Redis Stream，后续可按租户限制并发，避免一个租户批量导入拖垮其他人。

限流和预算都在**租户维度**，不是全局维度——这是多租户和单租户最实际的区别。

## 5. 数据生命周期

当前已具备：

- `ON DELETE CASCADE`：删除租户会级联删除业务数据；
- `kb_document` / `kb_chunk` 的删除会在同一事务内完成。

尚未实现：租户级导出、软删除保留期、异步物理清理。这些是上线前必须补的。

## 6. 怎么证明隔离有效

`TenantIsolationIT` 跑真实 PostgreSQL：

1. 在 acme 租户下建工单；
2. 切到 cloudwise 按 id 查 → 空；
3. 切到 cloudwise 列表 → 空；
4. 在 acme 上下文里写 cloudwise 的 `tenant_id` → 数据库策略拒绝；
5. 清空上下文查询 → 空。

这组测试比“代码里到处写 `WHERE tenant_id = ?`”更能证明隔离成立。

## 7. 已知边界

- 一个事务内切换租户不会重新设置 session 变量；当前请求模型是一请求一租户，不受影响；
- HNSW 索引是全局的，租户过滤在 ANN 之后发生；租户数量很大时要改为分区索引或 `hnsw.iterative_scan`；
- 平台管理员的跨租户查询目前只有仓库层，没有单独的管理端权限模型。
