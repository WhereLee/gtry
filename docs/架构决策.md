# 架构决策记录（ADR）

本文件记录最终方案中不可随意摇摆的决定。后续实现如果与这里冲突，先改 ADR，再改代码。

## ADR-001：模块化单体，不做微服务

**决定**：后端保持一个 Spring Boot 应用，按 `auth`、`tenant`、`ticket`、`wiki`、`ai`、`quota`、`notification`、`platform`、`audit` 划分模块。

**原因**：

- 目标客户是 0–100 人公司，单机 4C/4G 足够；
- 微服务会引入网关、服务发现、分布式事务和部署复杂度，收益为零；
- 模块化单体可以通过包边界、ArchUnit 和领域事件获得大部分可维护性。

**约束**：

- 模块之间只通过 service 或 `ApplicationEvent` 调用，不直接访问别的模块的 repository；
- `wiki` / `ai` 不依赖 `ticket` / `platform`；`ticket` 不依赖 `platform`；
- 新增跨模块调用必须补 ArchUnit 规则。

## ADR-002：共享库 + tenant_id + PostgreSQL RLS

**决定**：所有业务表共享一个 PostgreSQL，统一带 `tenant_id`，入口 JWT 决定租户，连接级 `app.tenant_id`，数据库 RLS 兜底。

**原因**：

- 每租户一个库/一个 schema 的运维成本不适合 0–100 人公司；
- RLS 能把“忘记加 tenant_id”变成数据库层拒绝，而不是靠 code review；
- 平台管理员通过 `app.platform_admin` 显式跨租户，普通请求永远不带这个标记。

**约束**：

- 公开接口不能从请求体接收 tenant_id，只能从 channel key / token 解析；
- 平台管理员上下文会绕过 RLS，所有跨租户查询必须显式带 `tenant_id`；
- 每个新表必须有 RLS 策略和隔离测试。

## ADR-003：事务性 outbox + Redis Stream，不引入 Kafka

**决定**：wiki 索引、通知、评测等异步任务使用 `outbox_event` + Redis Stream 消费者组；需要重投时用 `XAUTOCLAIM`，超过重试次数进 DLQ。

**原因**：

- 当前规模不需要 Kafka 的吞吐和生态；
- Redis 已经在用，Stream 的 consumer group/PEL 足够覆盖“至少一次 + 可重投”；
- outbox 保证“业务事务成功”和“事件一定被发布”一致。

**约束**：

- 业务写库和 outbox 写入必须在同一个事务；
- 消费者必须幂等，按 event id 去重；
- 失败事件不能静默 ACK，必须留在 PEL 或进 DLQ；
- 运维端点要能看到 pending、重投次数和 DLQ 数量。

## ADR-004：前端迁移到 Vue 3 + Element Plus

**决定**：最终形态使用 Vue 3 + Vite + TypeScript + Element Plus，三套界面：客户门户、坐席工作台、平台管理。

**原因**：

- 当前原生 JS 工作台适合演示，但继续叠加客户门户、团队管理、报表会不可维护；
- Element Plus 的表格、表单、弹窗、上传组件能显著降低后台界面成本；
- Vue 3 在国内中小公司招聘中更常见，和 Spring Boot 后端组合自然。

**约束**：

- 后端 API 保持稳定，前端迁移不改变业务语义；
- SSE 流式回复必须保留；
- 迁移完成前，原生 JS 只修 bug，不再加新页面。

## ADR-005：AI 工具调用必须有边界

**决定**：AI 可以调用只读工具（查订单、查客户、查历史工单），写操作（退款、改地址）只能生成草稿，必须由坐席确认后执行。

**原因**：

- 客服场景对错误写操作容忍度极低；
- 只读工具能显著提升回答质量，写操作保留人工责任边界；
- 这是“AI 落地”比“聊天机器人”更有价值的工程点。

**约束**：

- 工具按租户白名单注册，带 JSON Schema、超时和审计；
- 单次回答最多 3 步工具调用；
- 工具失败时回退到 RAG-only，不阻断回答；
- 所有工具调用写 `tool_call_log`，可在工单详情追溯。

## ADR-006：不做支付，只做用量与成本

**决定**：不接真实支付/计费，保留 token 用量、预算、限流、成本核算。

**原因**：

- 支付资质和真实资金链路不是这个项目的核心叙事；
- 用量与成本已经能支撑“B2B SaaS 成本控制”的面试问题；
- 把时间留给客户闭环、AI 质量和可靠性。
