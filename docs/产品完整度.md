# 产品完整度（P2）

P1 解决“回答可信不可信”，P2 解决“小公司拿到系统能不能真的用起来”。本阶段不引入支付、微服务或第二套向量库。

## 1. 工单分诊

创建工单时同步执行规则分诊，结果写入 `ticket.category`、`ticket.priority`、`assignee_id`、`triage_source`、`triage_reason`。

### 分类

规则按关键词打分，标题命中权重 2、正文命中权重 1，取最高分；没有命中进入 `OTHER`。

```text
RETURNS     退货、退款、换货、售后、维修
SHIPPING    物流、快递、发货、配送、地址、签收、运费
INVOICE     发票、抬头、税号、开票、冲红
PAYMENT     支付、扣款、付款、分期、银行卡
ACCOUNT     登录、密码、账号、验证码、找回
MEMBER      会员、积分、等级、优惠券、权益
PRODUCT     商品、规格、兼容、保修、说明书
PROMOTION   活动、满减、拼团、秒杀、价保
COMPLAINT   投诉、赔偿、态度、主管
QUOTA       配额、限制、存储、成员数、超限
BILLING     套餐、计费、续费、账单、订阅
PERMISSIONS 权限、角色、Owner、Admin、Guest、SSO
INTEGRATION 集成、Webhook、API Key、对接
SECURITY    2FA、审计、白名单、安全、风控
BACKUP      备份、恢复、容灾
UPGRADE     升级、降级、套餐变更
EXPORT      导出、下载
DELETION    删除、清理、注销
PRIVACY     隐私、个人信息、授权
SUPPORT     工单、客服、SLA、响应
OTHER       默认
```

### 优先级

| 级别 | 触发 |
|---|---|
| `URGENT` | 投诉、赔偿、欺诈、盗刷、泄露、无法登录、数据丢失、重复扣款、退款失败 |
| `HIGH` | 退款、退货、发票、超时、异常、失败、损坏、少件、丢件 |
| `LOW` | 咨询、建议、如何使用、了解、价格 |
| `NORMAL` | 其他 |

`COMPLAINT`、`PRIVACY`、`SECURITY`、`PAYMENT` 即使没有命中高风险词，也至少是 `HIGH`。

### 路由

按当前租户内 `AGENT` 优先、未关闭工单数最少、用户 ID 排序，选择负责人；没有可用坐席时保持未分配。

### 人工调整

```text
POST  /api/tickets/{id}/triage    重新跑规则
PATCH /api/tickets/{id}/triage    人工调整 category / priority / assigneeId
```

人工调整会把 `triage_source` 记为 `MANUAL`，便于和规则分诊区分。

## 2. 客服人工回复

工单详情页提供回复框，调用 `POST /api/tickets/{id}/messages`。

- 坐席回复后，`OPEN` / `CLOSED` 工单自动转为 `PENDING`；
- 消息以 `AGENT` 类型落库，与 `CUSTOMER`、`AI` 消息区分；
- `Ctrl+Enter` 可直接发送。

## 3. 用量面板

```text
GET /api/usage/summary          本月 tokens、预算、成本、限流
GET /api/usage/daily?days=14    按自然日聚合，缺失日期补 0
```

前端“用量”页展示本月 tokens、预算使用率、成本、限流和近 14 天柱状图。平台管理页的租户表同时展示每个租户的本月 tokens / 预算。

## 4. 平台租户管理

平台管理员登录后可见“平台”页。

### 开通

`POST /api/platform/tenants` 在一个事务内完成：

1. 创建 `tenant`；
2. 创建 `TENANT_ADMIN` 用户；
3. 创建默认知识空间 `default`；
4. 写平台审计。

### 停用/启用

`PATCH /api/platform/tenants/{id}/status?status=ACTIVE|SUSPENDED`。

`AuthService` 在登录时检查租户状态，停用租户返回 `tenant_inactive`，已有 token 仍受 RLS 约束。平台租户不能停用或删除。

### 导出

`GET /api/platform/tenants/{id}/export` 返回 JSON，包含：

- 租户信息；
- 用户（不含密码哈希）；
- 工单与消息；
- wiki 空间、页面、小节；
- 用量事件；
- 审计日志。

导出会写平台审计 `tenant.export`。

### 删除与回收站

`DELETE /api/platform/tenants/{id}?confirm={slug}`。

- 必须输入租户 slug 确认；
- 删除是软删除：状态置为 `DELETED`，写入 `deleted_at`，数据保留 30 天；
- `POST /api/platform/tenants/{id}/restore` 恢复为 `ACTIVE`；
- `DELETE /api/platform/tenants/{id}/purge?confirm={slug}` 才执行异步级联硬删除；
- `TenantPurgeScheduler` 每天 03:30 清理 `deleted_at` 超过 30 天的租户；
- `AuthService` 和 `TenantFilter` 都会拒绝非 `ACTIVE` 租户，已有 token 也会失效；
- `platform_audit_log` 不引用 `tenant(id)`，所以租户彻底删除后审计仍保留；
- 附件文件不在数据库级联范围内，生产环境需要额外的文件清理任务。

## 5. 数据库与审计

V4 迁移新增：

- `ticket.category`、`ticket.triage_source`、`ticket.triage_reason`；
- `ticket(tenant_id, category, created_at desc)` 索引；
- `platform_audit_log`（平台级，不随租户级联删除）。

## 5.1 客户门户

客户不需要账号，通过 channel key 进入：

```text
http://127.0.0.1:8091/portal.html?channel=acme-demo-key
http://127.0.0.1:8091/portal.html?channel=cloudwise-demo-key
```

流程：

1. `POST /api/public/tickets`，请求头 `X-Channel-Key`，服务端用
   `resolve_channel(key_hash)` 解析租户；
2. 创建工单后返回一次性展示的查询码（只存 SHA-256，不存明文）；
3. 客户用 `GET /api/public/tickets/{id}` + `X-Ticket-Token` 查询；
4. `POST /api/public/tickets/{id}/messages` 追加回复，工单回到 `OPEN`；
5. 工单关闭后 `POST /api/public/tickets/{id}/csat` 提交 1–5 分评价。

安全边界：

- `resolve_channel` / `resolve_ticket_token` 是窄范围的 `SECURITY DEFINER` 函数，
  只返回建立 TenantContext 所需的 id，真正的工单查询仍在 RLS 下执行；
- 公开接口按 channel / token 做 Redis 限流，Redis 不可用时降级放行并记录日志；
- 门户只返回 `visibility='PUBLIC'` 的消息，AI 建议和内部备注都是 `INTERNAL`。

## 5.2 内部备注与 CSAT

- 坐席回复框勾选“内部备注”后调用 `POST /api/tickets/{id}/notes`，消息
  `visibility='INTERNAL'`，不会进入客户门户；
- AI 建议也以 `INTERNAL` 落库，避免把草稿发给客户；
- 客户评分写入 `ticket.csat_rating/csat_comment/csat_at`，坐席详情页可见。

### 附件

- 客户和坐席都可以上传图片、PDF、纯文本，单文件上限 10MB；
- 文件保存在 `helpdesk.attachments.dir`，数据库只存 storage key；
- 附件有 `PUBLIC/INTERNAL` 可见性，客户门户只列出和下载 `PUBLIC`；
- 文件名会做安全清洗，路径做 `normalize` + `startsWith` 校验，防止目录穿越。

## 5.3 团队成员

租户管理员在“团队”页调用：

```text
GET   /api/users
POST  /api/users
PATCH /api/users/{id}
```

角色只允许 `AGENT` / `TENANT_ADMIN`；停用后该用户无法登录，不能停用当前登录账号。

## 6. Wiki 版本与审批

V12 迁移新增 `wiki_page_version`：

```text
id, tenant_id, page_id, version, title, visibility, status,
sections jsonb, created_by, created_at
```

流程：

1. 新建/编辑页面保存为 `DRAFT`，同时写入一条版本快照；
2. `POST /api/wiki/pages/{id}/submit` 进入 `REVIEW`；
3. `POST /api/wiki/pages/{id}/approve` 进入 `PUBLISHED`，记录复核时间；
4. `POST /api/wiki/pages/{id}/reject` 退回 `DRAFT`；
5. `GET /api/wiki/pages/{id}/versions` 查看版本列表；
6. `GET /api/wiki/pages/{id}/versions/{version}` 查看版本正文；
7. `POST /api/wiki/pages/{id}/rollback/{version}` 回滚，回滚本身会追加一个新版本。

检索只返回 `status='PUBLISHED'` 的页面，草稿和待审核内容不会进入 AI 知识库。
前端知识库页展示状态标签、提交/通过/驳回按钮和版本历史对话框。

### 其他边界

- 分诊是规则引擎，不是 LLM 分类；这样不依赖外部模型，延迟稳定，也便于解释。需要 LLM 时可以把 `TicketTriageService` 作为兜底，在前面加一层模型分类。
- 平台审计目前只入库，没有平台审计查询页；数据已经在，后续加一个只读接口即可。
- 版本历史当前是正文快照和回滚，没有并排 diff；需要时可以在前端增加 diff 视图。
- 审批通过/驳回目前不发送通知，后续可接邮件或站内信。
