# 压测与故障注入

## 1. 环境

- 本机 Windows，Java 17，Spring Boot 3.3.5
- PostgreSQL 18 + pgvector，Redis 7
- 应用：`-Xmx768m`，Hikari `maximum-pool-size=12`
- LLM / embedding：mock（排除外部 API 和模型加载对结果的干扰）
- 数据库：`helpdesk_e2e`

## 2. 压测工具

仓库内置一个无第三方依赖的 Java 单文件工具：`tools/LoadTest.java`。

```powershell
# 先启动一个 8092 端口的实例（mock provider）
java tools/LoadTest.java http://127.0.0.1:8092 acme agent@acme.test agent123 32 500
```

参数依次为：baseUrl、租户、邮箱、密码、并发数、请求数。工具会先登录，预热 20 次，
然后并发请求 `GET /api/tickets`，输出吞吐、错误数、p50/p95/p99、最小/最大延迟。

## 3. 基线结果

| 并发 | 请求数 | 成功 | 错误 | 总耗时 | RPS | p50 | p95 | p99 | min | max |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 32 | 500 | 500 | 0 | 760ms | 657.9 | 44ms | 90ms | 123ms | 7ms | 188ms |
| 64 | 1000 | 1000 | 0 | 1024ms | 976.6 | 48ms | 167ms | 230ms | 4ms | 418ms |
| 128 | 2000 | 2000 | 0 | 1727ms | 1158.1 | 81ms | 300ms | 524ms | 4ms | 798ms |

结论：

- 读路径在 128 并发、2000 请求下仍然 0 错误，吞吐约 1.1k RPS；
- p99 随并发上升主要来自 Hikari 连接池（12）和本机 CPU 竞争，不是业务逻辑死锁；
- 对 10–100 人公司的内部客服场景，这个容量有充足余量；
- 公网 3M 带宽主要影响首次静态资源加载和附件下载，不影响 JSON API 的并发能力。

## 4. 故障注入

### 4.1 Redis 不可用

启动一个连接不存在 Redis 端口的实例：

```powershell
$env:SERVER_PORT='8093'
$env:REDIS_PORT='6399'
java -jar target\helpdesk-0.1.0.jar
```

实测结果：

- `/actuator/health` 返回 `503`（Redis 健康检查失败）；
- 登录成功，`GET /api/tickets` 成功（登录限流、JWT 撤销检查降级放行）；
- 日志出现：
  - `helpdesk_login_rate_limit_unavailable`
  - `helpdesk_token_check_unavailable`
  - `helpdesk_index_stream_poll_failed`

这是有意的降级：Redis 短时不可用时，核心工单链路不被阻断；但限流、撤销和异步索引会暂时失效/暂停。

### 4.2 LLM 不可用

用缺失或错误的 `HELPDESK_LLM_API_KEY` 调用 AI 建议：

- 应用重试 1 次后返回固定降级话术；
- 记录 `helpdesk_llm_failed`，并累加 `helpdesk_llm_fallback_total`；
- 前端展示“AI 服务暂时不可用，请稍后重试，或直接转人工客服处理。”。

对应单元/集成测试：`RagServiceTest`、`AiFlowTest`。

### 4.3 PostgreSQL 不可用

PostgreSQL 是强依赖，没有进程内降级：

- `/actuator/health` 变为 `DOWN`；
- 工单、登录、知识库接口返回 5xx；
- 恢复方式：重启 PostgreSQL，确认 `pg_isready`，再检查应用健康。

这类故障依赖备份/恢复和单机重启，不做“假成功”降级。

### 4.4 索引消费者积压

Redis 不可用或消费者停止时：

- `GET /api/admin/outbox/status` 的 `pending` 增长；
- `GET /api/admin/index/status` 的 `pendingIndexEvents` 增长；
- 页面保存本身仍然成功，检索会暂时使用旧索引；
- Redis 恢复后 Stream 消费继续，PEL 中的未确认消息会重投，失败消息进入 DLQ。

### 4.5 SLA 超时

可以手工把某条工单的 `sla_due_at` 改成过去时间，等待 `SlaScheduler` 下一分钟扫描：

```sql
UPDATE ticket SET sla_due_at = now() - interval '5 minutes' WHERE id = '...';
```

预期：

- `ticket.sla_breached = true`；
- `helpdesk_sla_breaches_total` 增加；
- `GET /api/tickets/breached` 能查到该工单。

## 5. 复现与限制

- 压测工具是轻量基线工具，不是 k6/Gatling 的替代品；没有模拟网络延迟、TLS、慢客户端；
- 结果依赖本机 CPU、磁盘和数据库状态，换机器需要重新跑；
- 生产环境建议用 k6 对登录、工单列表、工单详情、AI 建议分别建场景，并在测试环境注入 Redis/LLM/PostgreSQL 故障；
- 当前结论用于证明容量趋势和降级行为，不用于承诺生产 SLA。
